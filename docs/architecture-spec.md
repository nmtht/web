# name that! — Техническое задание на архитектуру сайта

Версия 1.0 · черновик для обсуждения с разработчиком

Источник истины по поведению: рабочий HTML-прототип (`nt-website.html` / `/prototype/index.html`). Этот документ описывает, как перенести его логику в продакшн-архитектуру с Headless CMS, а не переизобретает эту логику — при любом расхождении прототип имеет приоритет, а это ТЗ нужно править.

---

## 1. Цель

Сайт-практика `name that!` — не портфолио со страницами, а исследуемая карта мышления: force-directed граф, где проекты, исследования, вопросы и теги — узлы одной системы, а не разделы меню. Сейчас это реализовано как один HTML-файл с захардкоженными данными. Задача — вынести контент в Headless CMS (Sanity), чтобы автор мог сам добавлять и редактировать проекты, исследования, вопросы и связи между ними, не трогая код, и пересобрать интерактив на нормальном фреймворке вместо одного файла.

## 2. Технологический стек

| Слой | Решение | Почему |
|---|---|---|
| CMS | **Sanity** (Content Lake + Studio) | Уже выбран заказчиком как референс |
| Фреймворк | **Astro**, islands-архитектура | Сайт почти целиком статичен, кроме одного тяжёлого интерактивного острова (граф). Не нужен полный React SPA ради одной страницы |
| Интерактивный остров | React или Vue-компонент внутри Astro island (`client:only` или `client:load`) | D3 плохо дружит с SSR — граф должен монтироваться только на клиенте |
| Граф / физика | **D3-force** (d3-force, d3-drag, d3-zoom) — оставить, уже проверено и работает | Не нужно переписывать на другую библиотеку, логика физики переносится почти без изменений |
| Стили | Как сейчас: CSS-переменные, без CSS-фреймворка | Проект целиком монохромный и типографический, Tailwind/UI-кит не нужен |
| Деплой контента | Инкрементальная сборка по вебхуку из Sanity (Astro `getStaticPaths` + ревалидация, либо hybrid rendering) | Автор публикует в Sanity → сайт пересобирается сам |

**Альтернатива:** Next.js вместо Astro, если разработчику будущего проекта удобнее React везде. Технически оправдано, но при 95% статичного контента Astro даёт меньше JS на клиенте и проще ментальную модель. Финальный выбор — за разработчиком, здесь не принципиально.

### Важное архитектурное решение: отказ от `<foreignObject>`

Сейчас каждый узел графа — это `<foreignObject>` внутри SVG с обычным HTML внутри. Это позволило быстро сделать прототип, но `foreignObject` + 3D CSS-трансформации (барабан) — известное слабое место Safari.

**В продакшн-версии:** узлы рендерятся как обычные HTML-элементы с `position: absolute; transform: translate(x, y)` поверх контейнера, а SVG используется **только** для линий-связей (`<path>` между узлами), поверх/под HTML-слоем через `z-index`. Позиции по-прежнему считает D3-force на каждый `tick`, просто применяются к HTML, а не к атрибутам `foreignObject`. Это решает Safari-проблему на уровне архитектуры, а не патчами.

## 3. Модель контента (Sanity Schema)

### 3.1 Локализация

Сейчас каждое переводимое поле в прототипе — объект `{ en, ru }`. Предлагается сохранить этот принцип и в Sanity: **не** document-level i18n (отдельные документы на каждый язык), а **field-level** объекты через кастомный тип `localeString` / `localeText`, как в стандартном рецепте Sanity (`{ _type: 'localeString', en: string, ru: string }`). Причины:
- Связи (`tags`, `leads`) не дублируются между языками — они у сущности одни;
- Проще для автора: редактирует один документ, оба языка рядом.

**Не переводится:** `nt!`, `name that!`, названия проектов/исследований (собственные имена), названия соцсетей — это зафиксировано как принцип бренда, не поле для регулярного редактирования, скорее всего может остаться в коде/константах, а не в CMS.

### 3.2 Document types

**`project`** (= THAT!)
- `title` — string (не переводится)
- `slug`
- `meta` — localeString (город/год, например «Moscow, RU / 2025»)
- `kind` — localeString (тип работы)
- `body` — localeText
- `images` — array of image (с hotspot), 1–3 штуки, порядок = порядок в барабане
- `tags` — array of reference → `tag`

**`research`** (= THINK)
- те же поля, что у `project`, плюс:
- `kind` в прототипе играет роль «категории» (Observation / Software / Text / Speculative) — сделать как select с предустановленными вариантами + возможность вписать свой
- `images` — 0–3 штуки (допускается пусто, барабан в этом случае не строится)

**`question`** (= WHAT IF?)
- `title` — localeText (вопрос целиком, с «what if…?»)
- `tags` — array of reference → `tag`
- `leads` — array of reference → `project` | `research` (полиморфная ссылка, в Sanity — `reference` с `to: [{type:'project'},{type:'research'}]`)

**`tag`**
- `key` — string, slug-подобный уникальный идентификатор (используется в логике связей, не менять после создания)
- `label` — localeString (то, что видит пользователь)

**`practiceInfo`** (singleton, раздел NEXT)
- `inviteLine` — localeString
- `practiceDescription` — localeText
- `authorName` — string
- `authorRole` — localeString
- `authorBio` — localeText
- `contactEmail` — string
- `contactNote` — localeString
- `socialLinks` — array of `{ label: string, url: url }`

**`uiStrings`** (singleton, служебные подписи интерфейса)
- Все статические UI-строки, которые сейчас лежат в объекте `UI` в коде (подсказка внизу, «reset map», лейблы «Tags» / «Related» / «Leads to» и т.д.) — тоже localeString-поля, чтобы автор мог их поправить без разработчика.

### 3.3 Правило целостности (важно предупредить редактора/разработчика)

Каждый `project`/`research` должен быть связан **хотя бы с одним** `question` через его поле `leads` — иначе в графе этот узел никогда не появится (правило «только через вопрос», см. п. 4.2). Это не выражается штатными средствами Sanity-валидации напрямую (обратная ссылка), но стоит либо:
- добавить custom-валидацию в Studio (плагин/скрипт, который проверяет обратные ссылки), либо
- обучить автора этому правилу и полагаться на review при публикации.

Разработчику стоит на старте реализовать хотя бы простой GROQ-запрос «показать все project/research без единого question, который на них ссылается» — как чек-лист перед деплоем.

## 4. Функциональные требования (зафиксировано в прототипе)

Ничего из этого не нужно придумывать заново — задача переноса, а не редизайна. Ниже — список как чек-лист для разработчика и как раздел ТЗ для приёмки.

### 4.1 Вход на сайт
- Прелоадер на белом фоне: `name that!` быстро печатается и сжимается до `nt!`, затем исчезает.
- После прелоадера — граф с единственным узлом «name what's next.» по центру.
- Наведение на этот узел (только в EN) — сжимается до «nt», при уходе курсора — разворачивается обратно. В RU — статичный переведённый текст без этого трюка.

### 4.2 Логика графа
- Клик по seed-узлу → расходятся три узла: `THAT!`, `THINK`, `NEXT` (радиально, под фиксированными углами).
- Клик по `THAT!`/`THINK` → раскрываются **только** связанные `question`-узлы (не проекты/исследования напрямую).
- Клик по `question` → раскрывается project/research, к которым он ведёт (`leads`). Прямой связи «раздел → лист» быть не должно — только через вопрос. Если у листа есть связь с другим разделом через общий вопрос — она сохраняется.
- Клик по `tag` → подтягивает в граф все project/research с этим тегом, независимо от того, раскрыта ли их «официальная» ветка.
- Повторный клик по уже раскрытому `THAT!`/`THINK`/`NEXT`/seed — сворачивает всё, что было раскрыто **только** через него (reachability-check: если узел всё ещё достижим через другую ветку — он остаётся).
- `NEXT` не раскрывает детей — сразу открывается как барабан (см. 4.3).

### 4.3 Открытие проекта/исследования/NEXT — 3D-барабан
- Не модальное окно — узел физически увеличивается **прямо в графе** (тот же принцип: остаётся частью физической симуляции, соседние узлы раздвигаются).
- Изометрический наклон (`rotateX`) + вращение вокруг своей оси (`rotateY`) — все изображения видны одновременно, ничего не «появляется из ниоткуда» при повороте.
- Каждая карточка изображения — двусторонняя (`front`/`back`, `backface-visibility: hidden`, `rotateY(180deg)` на обратной грани), чтобы текст/картинка не зеркалились при повороте на 180°.
- Текстовые подписи (заголовок+метаданные / описание / связанное) закреплены в тех же 3D-координатах и вращаются вместе с барабаном, на фиксированных углах (не завязаны на количество картинок — работает и с 1 картинкой, и с 3).
- Вращение — драгом (мышь/тач) и автоматическое медленное вращение, когда пользователь не взаимодействует.
- Можно открыть **несколько** узлов одновременно — открытие одного не закрывает другой.
- Закрытие: крестик **или** клик в пустой центр барабана.
- У проекта/исследования нет тегов и рамки внутри барабана — только заголовок, метаданные, картинки, описание, связанное.
- `NEXT` — та же механика барабана, но без картинок: три текстовых блока (приглашение+описание практики / об авторе / контакты и соцссылки), тоже вращаются, тоже закрываются по центру.

### 4.4 Общее «оживление» поля
- Все узлы графа медленно и хаотично дрейфуют по полю (случайная целевая точка каждые ~4 сек, плавное подтягивание к ней).
- Не дрейфует: узел, который пользователь сейчас перетаскивает вручную; открытый барабан (у него своя анимация — вращение).
- Логотип `nt!` в шапке — тоже перетаскиваемый элемент поля. Обычный клик (без значимого перемещения) — сбрасывает карту и возвращает логотип на место с анимацией; при активном перетаскивании клик не срабатывает.

### 4.5 Взаимодействие с полем
- Зум колёсиком/пинчем, панорамирование перетаскиванием пустого места.
- Перетаскивание отдельного узла — закрепляет его на месте (перестаёт участвовать в хаотичном дрейфе и в силовой симуляции).
- Кнопка «reset map» — полный сброс: граф, зум, позиция логотипа.

### 4.6 Фирменный приём наведения
- Единый визуальный язык: у любого интерактивного текстового элемента (пункты навигации, теги, кнопка «Let's talk», ссылки) при наведении/фокусе шрифт переключается на курсивный дисплейный (Latin Modern Math) и текст становится строчным. Реализовано одним переиспользуемым CSS-классом — сохранить этот подход, не размножать частные реализации.

### 4.7 Локализация
- Переключатель RU/EN, кнопка без рамки, нижний правый угол.
- Переводится весь контент и весь интерфейс, включая `THAT!`/`THINK`/`NEXT` и hero-фразу «name what's next.» — **кроме** словесного знака `nt!` / `name that!` (бренд-марка).
- Английская hover-анимация «сжатие до nt» — только в EN-режиме (в RU у фразы нет такой игры букв).

## 5. Нефункциональные требования

- **Производительность.** Граф рассчитан на десятки узлов одновременно (не тысячи) — это карта одной практики, не дата-визуализация большого датасета. D3-force на таком объёме не требует виртуализации или воркеров.
- **Safari/кроссбраузерность.** См. архитектурное решение в п. 2 (отказ от `foreignObject`). Плюс: везде, где остаются 3D CSS-трансформации (барабан), дублировать свойства с `-webkit-`-префиксом.
- **`prefers-reduced-motion`.** Уже заложено в прототип как принцип — все анимации (прелоадер, дрейф, вращение барабана, hover-трюки) должны либо отключаться, либо резко сокращаться при этом медиа-запросе. Перенести как обязательное требование, не опцию.
- **Доступность.** Фокус-стейты на всех интерактивных элементах, ARIA там, где кнопки не самоочевидны (крестик закрытия, стрелки барабана). Полная навигация графа с клавиатуры — не критична (это исследовательский, не транзакционный интерфейс), но базовая доступность (фокус видим, `aria-label` есть) обязательна.
- **SEO.** Поскольку основной контент (проекты/исследования) не существует как отдельные URL в текущей модели (всё — состояния одного графа), для SEO может понадобиться параллельно генерировать статические «тихие» страницы вида `/projects/gorky-edge` (простой текст + картинки, без графа) специально для индексации и шаринга ссылок — **это открытый вопрос, см. п. 7**.

```
  /components

      NodeSeed.*
      NodeMain.*

      NodeQuestion.*
      NodeTag.*

      DrumFace.*                  — двусторонняя грань (картинка или текст)
    Header.*                      — логотип (draggable) + reset

  /schemas
    project.ts, research.ts, question.ts, tag.ts, practiceInfo.ts, uiStrings.ts, localeString.ts, localeText.ts
```

## 7. Открытые вопросы (нужно решить до старта разработки)

1. **SEO/шаринг отдельных проектов.** Нужны ли отдельные индексируемые URL на каждый проект (для поисковиков, для отправки прямой ссылки коллеге), или сайт полностью остаётся единой точкой входа `/`? Если да — это доп. работа (генерация статических «карточек» параллельно с графом).
2. **Порог количества контента.** Текущая физика (радиусы, дистанции связей, коллизии) откалибрована на ~20 узлов. Если автор со временем добавит 50+ проектов, потребуется ли группировка/фильтрация, или это осознанно остаётся компактной картой?
3. **Черновики/неопубликованные материалы.** Нужен ли в Sanity статус «черновик», не видимый на проде, или всё, что в CMS, — сразу публично?
4. **Кто пишет вопросы (`question`)?** Раз каждый project/research обязан быть связан хотя бы с одним вопросом — включаем ли это явно в UX Sanity Studio (например, подсказка «этот проект ничего не ведёт», см. п. 3.3), или полагаемся на дисциплину автора?
5. **Домен/хостинг.** Astro + Sanity обычно деплоятся на Vercel/Netlify — есть ли уже предпочтение?
